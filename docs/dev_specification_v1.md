# 世尚门店订货系统开发规范 v1.0

更新日期：2026-08-17  
适用项目：世尚智能悬浮卷帘门店订货系统  
关联需求：[《世尚门店订货系统 PRD v3.1》](./世尚门店订货系统_PRD_v3.1.md)  
适用人员：产品、UI、前端、后端、测试、运维及参与开发的AI Agent。  
规范级别：项目强制规范。除标注“建议”的内容外，开发、测试和部署均须遵守。

---

## 一、规范目标

本规范用于保证世尚门店订货系统在以下方面保持一致和可控：

- 微信小程序、H5和管理后台使用统一业务规则；
- 价格、库存、支付、订单状态及归属关系准确；
- 历史订单不被当前商品、供应商或销售关系变化污染；
- 系统支持门店、城市合伙人和公司销售的CRM归属；
- 开发产出可追踪、可测试、可部署、可回滚；
- AI生成代码必须经过规范约束和人工审查后才能进入生产。

优先级顺序：

> 数据正确性与资金安全 > 权限与隐私 > 可追溯性 > 可维护性 > 性能 > 开发速度

## 二、统一技术栈

### 2.1 后端

- PHP 8.1及以上；
- ThinkPHP 8；
- MySQL 8.0及以上；
- Redis；
- Workerman，用于WebSocket实时通知；
- Composer；
- Nginx；
- Docker与docker-compose；
- Git。

### 2.2 门店订货端

同时发布微信小程序和H5，统一采用：

- uni-app；
- Vue 3 Composition API；
- TypeScript；
- Pinia；
- pnpm；
- 与uni-app兼容的UI组件库。

门店订货端不得直接使用只能运行在浏览器DOM中的Element Plus或Vant Web组件。若H5使用Vant专属组件，必须提供小程序端对应实现，不得影响业务功能一致性。

### 2.3 公司管理后台

- Vue 3 Composition API；
- TypeScript；
- Vite；
- Pinia；
- Vue Router 4；
- Element Plus；
- pnpm。

### 2.4 数据权威

MySQL是以下数据的最终权威来源：

- 客户、门店、城市合伙人和销售归属；
- 商品、价格和价格版本；
- 套件库存及库存流水；
- 订单、订单明细和状态；
- 支付、退款和发票；
- 面料及供应商映射；
- 审批和操作日志。

Redis只用于：

- 缓存；
- 手机验证码；
- 接口限流；
- 短期幂等标记；
- WebSocket连接映射；
- 任务协调和辅助锁。

禁止仅在Redis中保存最终库存、支付结果、订单金额、历史价格或归属快照。

## 三、环境与配置

### 3.1 环境划分

至少划分：

- `local`：本地开发；
- `test`：集成测试；
- `staging`：预发布验收；
- `production`：生产。

不同环境使用独立数据库、Redis、支付配置和文件存储。禁止测试环境直接连接生产数据库。

### 3.2 环境变量

- 所有密钥、证书路径、数据库密码和支付配置通过环境变量或安全配置注入；
- `.env`及真实证书不得提交Git；
- 仓库只提供`.env.example`；
- 环境变量使用`UPPER_SNAKE_CASE`；
- Docker镜像必须使用明确版本，不使用`latest`；
- `composer.lock`和`pnpm-lock.yaml`必须提交。

示例：

```env
APP_ENV=production
APP_DEBUG=false
DB_HOST=mysql
DB_PORT=3306
DB_DATABASE=shishang_order
REDIS_HOST=redis
WECHAT_MCH_ID=
ALIPAY_APP_ID=
```

### 3.3 时间与时区

- 系统业务时区统一使用`Asia/Shanghai`；
- API日期时间使用ISO 8601格式并包含时区；
- 数据库时间字段规则全项目统一，不允许同一项目混用本地时间和UTC；
- 订单价格锁定和支付超时均按服务器时间计算。

## 四、项目架构与职责

### 4.1 后端分层

```text
Controller
  → Request / Validate
  → Application Service
  → Domain Service
  → Repository / Model
  → Infrastructure
```

职责：

- Controller：接收请求、调用服务、返回响应；
- Validate：验证字段、类型、格式和基础范围；
- Application Service：组织完整用例；
- Domain Service：实现计价、库存、状态机、归属和支付等核心规则；
- Repository/Model：数据查询和持久化；
- Infrastructure：微信、支付宝、短信、文件、WebSocket及外部系统适配。

禁止：

- Controller直接扣库存；
- Controller直接修改订单状态；
- Controller直接处理支付回调业务；
- 在Model事件中隐藏执行跨模块核心业务；
- 多处复制同一计价公式。

### 4.2 核心服务

至少建立：

- `PricingService`：后端计价；
- `InventoryService`：库存锁定、核销、释放和流水；
- `OrderService`：订单创建和变更；
- `OrderStateService`：订单及明细状态转换；
- `OwnershipService`：门店、合伙人和销售归属；
- `PaymentService`：支付下单、回调、查单和退款；
- `InvoiceService`：开票申请和状态；
- `FabricSupplierService`：面料与供应商映射；
- `AuditService`：关键操作审计；
- `NotificationService`：站内、订阅消息及WebSocket通知。

### 4.3 前端分层

建议：

```text
pages / views
components
stores
services / api
composables
types
utils
constants
```

- 页面不得直接拼接API URL；
- 页面不得自行决定最终价格；
- 所有API调用集中在`services/api`；
- Pinia按业务域拆分；
- 公共类型集中维护；
- 平台差异封装，不在业务页面大量散落条件编译。

## 五、命名规范

### 5.1 数据库

- 表名：`lj_`前缀＋`snake_case`；
- 字段：`snake_case`；
- 主键：`id`；
- 外键字段：`xxx_id`；
- 布尔字段：`is_xxx`或`has_xxx`；
- 时间字段：`created_at`、`updated_at`、`deleted_at`；
- 唯一业务编号：`xxx_no`；
- 金额分字段：`xxx_amount_cent`或`xxx_price_cent`。

示例：

```text
lj_orders
lj_order_items
lj_store_inventory
lj_inventory_transactions
lj_payment_transactions
lj_customer_ownership_history
```

### 5.2 API

- 路径：RESTful、复数资源名、kebab-case；
- 统一版本前缀：`/api/v1`；
- JSON字段统一使用`snake_case`；
- 查询参数使用`snake_case`。

示例：

```text
POST /api/v1/orders
GET  /api/v1/orders/{order_no}
POST /api/v1/orders/{order_no}/price-preview
POST /api/v1/orders/{order_no}/payments
POST /api/v1/payment-callbacks/wechat
GET  /api/v1/fabrics?page=1&page_size=20
```

### 5.3 PHP

- 类名：PascalCase；
- 方法、变量：camelCase；
- 常量：UPPER_SNAKE_CASE；
- 接口：以`Interface`结尾；
- 异常：以`Exception`结尾；
- 服务：以`Service`结尾；
- 数据传输对象：以`DTO`结尾。

### 5.4 Vue与TypeScript

- 组件文件：PascalCase；
- 组合式函数：`useXxx`；
- Store：`useXxxStore`；
- 普通变量和函数：camelCase；
- 常量：UPPER_SNAKE_CASE；
- 类型和接口：PascalCase。

## 六、编码规范

### 6.1 PHP

- 遵循PSR-12；
- 使用Composer自动加载；
- 新文件开启严格类型；
- 公共类、接口和复杂业务方法编写PHPDoc；
- 所有API必须进行输入验证；
- 所有外部调用必须处理超时和异常；
- 禁止吞掉异常；
- 禁止在生产响应中返回堆栈、SQL和服务器路径；
- 核心业务禁止使用魔法数字，价格和状态使用常量或配置；
- 不允许复制粘贴计价、库存和状态逻辑。

### 6.2 TypeScript

- 开启`strict`；
- 禁止显式`any`；
- 不确定类型使用`unknown`并进行类型收窄；
- API请求和响应必须定义类型；
- 禁止`@ts-ignore`，确有需要必须写明原因并经审查；
- 使用ESLint和Prettier；
- 提交前必须通过类型检查和构建；
- 公共方法和复杂逻辑必须有注释。

### 6.3 注释原则

注释说明“为什么”和业务约束，不重复代码本身。以下逻辑必须注明来源：

- PRD条款；
- 价格公式；
- 库存事务；
- 支付幂等；
- 状态转换；
- 快照和归属规则；
- 特殊兼容处理。

引用其他Agent产出时，在文档或代码审查说明中注明来源、文件和版本。

## 七、数据库规范

### 7.1 基础要求

- MySQL 8、InnoDB、`utf8mb4`；
- 主键建议使用`BIGINT UNSIGNED`；
- 表和关键字段必须有注释；
- 数据库结构变更使用Migration；
- 禁止直接在生产环境手工改表；
- 已被订单引用的主数据禁止物理删除；
- 软删除数据仍须满足历史查询；
- 高频过滤、关联和唯一业务键必须建立索引；
- 禁止N+1查询；
- 所有动态排序字段使用白名单。

### 7.2 金额和尺寸

金额统一以“分”为最小存储单位，使用整数：

```text
unit_price_cent BIGINT
subtotal_amount_cent BIGINT
paid_amount_cent BIGINT
refund_amount_cent BIGINT
```

禁止金额字段使用`FLOAT`、`DOUBLE`。

尺寸和面积：

```text
width_cm  DECIMAL(6,1)
height_cm DECIMAL(6,1)
area_m2   DECIMAL(12,4)
```

- 输入宽高单位为厘米，保留1位小数；
- 计算时转换为米；
- 面积为宽×高；
- 面积中间结果至少保留4位小数；
- 金额采用普通四舍五入`ROUND_HALF_UP`至分；
- 每副窗帘先计算到分，再汇总订单；
- 禁止使用PHP float或JavaScript Number作为最终结算依据。

### 7.3 唯一约束

至少对以下字段设置唯一约束：

- 门店编号；
- 城市合伙人编号；
- 订单号；
- 订单明细编号；
- 支付单号；
- 支付平台交易号；
- 库存流水业务幂等键；
- 世尚面料编号；
- 同一客户主体内有效账号关联。

### 7.4 历史和快照

订单必须保存下单或生产时的快照，不能只查询当前主数据：

- 客户名称和编号；
- 城市合伙人；
- 成交销售；
- 当前服务销售；
- 收件人和地址；
- 商品名称、编号和价格；
- 面料编号和成交价格；
- 实际供应商、供应商原始编号和批次；
- 价格版本和公式版本。

修改主数据不得改变历史订单展示和统计。

## 八、计价规范

### 8.1 最终计价权

- 前端只提供即时预览；
- 后端是最终计价权威；
- 前端提交尺寸、商品编号、数量和库存抵扣选择；
- 后端重新读取客户等级、价格版本和商品价格；
- 后端计算结果与支付金额必须一致；
- 支付前再次校验价格锁定状态。

### 8.2 标准公式

单副窗帘：

```text
横轨费用 = 宽度（米） × 横轨后台有效单价
竖轨费用 = 高度（米） × 2 × 竖轨后台有效单价
面料费用 = 宽度（米） × 高度（米） × 面料编号后台有效单价
选装费用 = Σ（选装商品单价 × 数量）
套件费用 = 未抵扣套件数量 × 客户有效套件价格
单副金额 = 横轨 + 竖轨 + 面料 + 选装 + 套件 + 非标费用
```

- 不收包装费；
- 物流到付，不进入线上支付金额；
- 认证门店套件价760元含税、不含运费；
- 城市合伙人套件价660元含税、不含运费；
- 体验客户和特殊合同客户一客一定；
- 所有价格从后台读取，禁止在代码中硬编码。

### 8.3 价格版本

- 每次价格调整产生新版本；
- 订单保存价格版本；
- 价格锁定30天；
- 30天后未支付，订单失效并重新计价；
- 历史订单不受新价格影响；
- 人工改价必须审批并保存改价前后金额和原因。

## 九、库存与并发规范

### 9.1 库存模型

套件库存区分：

- 可用；
- 锁定；
- 核销；
- 释放；
- 售后冻结；
- 退回待检。

### 9.2 并发控制

- 库存操作必须在后端完成；
- 使用数据库条件更新、乐观锁或行级锁保证不超卖；
- Redis锁只能辅助，不能代替数据库一致性；
- 同一库存不得被两个订单重复锁定；
- 库存不可为负数；
- 所有库存变化必须生成流水；
- 每个库存操作使用唯一幂等键；
- 同一幂等键重复请求返回原结果，不重复执行。

### 9.3 事务边界

同一本地事务应完成：

- 校验库存；
- 锁定或核销库存；
- 写库存流水；
- 更新订单相关状态；
- 写必要的Outbox事件。

事务内禁止调用微信、支付宝、短信等外部网络服务。

支付平台不属于MySQL事务。支付成功后的生产任务创建失败时：

- 不回滚外部支付事实；
- 订单进入待补偿状态；
- 自动重试生产任务；
- 多次失败后进入人工处理；
- 必要时发起退款。

### 9.4 对账

定时核对：

- 订单与库存锁定；
- 支付结果与订单实付；
- 核销数量与订单明细；
- 退款与库存释放；
- 异常结果生成告警和人工任务。

## 十、订单状态机规范

### 10.1 统一入口

- 所有状态变化必须通过`OrderStateService`；
- 禁止直接更新订单状态字段；
- 每个转换规定来源状态、目标状态、角色、条件和副作用；
- 非法转换返回4xxx业务错误；
- 每次转换写入状态历史。

### 10.2 主订单和明细

- 每副窗帘拥有独立生产、质检和发货状态；
- 主订单状态由明细聚合；
- 部分明细发货时主订单为“部分发货”；
- 全部明细发货后主订单为“已发货”；
- 不能只修改主订单而忽略明细。

### 10.3 关键限制

- 已取消订单不能进入生产；
- 已发货订单不能直接修改地址；
- 进入生产后门店不能取消；
- 后台管理员特殊取消需要权限、原因和审批；
- 取消必须处理库存、支付、材料成本和退款；
- 状态转换和副作用必须具备自动化测试。

## 十一、客户和销售归属规范

### 11.1 三层归属

- 交易主体：实际下单付款的门店或城市合伙人；
- 渠道归属：门店所属城市合伙人，可为空；
- 公司销售归属：公司内部主维护销售。

门店归合伙人时，自动继承合伙人的公司销售。没有城市合伙人时，门店直接归公司销售。

### 11.2 销售转交

销售离职或调岗：

- 在合伙人层级执行转交；
- 同步更新其有效下属门店当前维护销售；
- 转交未完成商机、任务、订单和售后；
- 保留原销售、接任销售、时间、原因和审批记录；
- 新订单使用新销售；
- 历史订单成交销售不自动改变。

### 11.3 订单归属快照

订单保存：

- 交易主体；
- 实际服务门店；
- 城市合伙人；
- 成交销售；
- 当前服务销售；
- 协同销售；
- CRM客户及商机ID；
- 归属确定时间和规则。

历史业绩统计必须读取订单快照，不得直接读取客户当前销售。

## 十二、支付与退款规范

### 12.1 支付适配器

微信和支付宝分别实现统一支付接口：

- 创建支付；
- 验签回调；
- 主动查单；
- 关闭订单；
- 发起退款；
- 查询退款。

### 12.2 支付安全

- 回调必须验签；
- 回调必须幂等；
- 支付平台交易号唯一；
- 订单号、金额、商户号必须匹配；
- 不以前端支付成功页面作为到账依据；
- 回调延迟时使用主动查单；
- 原始回调脱敏保存；
- 支付证书和密钥不得进入Git和日志。

### 12.3 支付超时

- 订单支付超时30天；
- 超时后释放库存锁定；
- 超时订单不能继续使用旧价格；
- 重新购买必须按当前价格重新提交。

### 12.4 退款

- 退款必须有权限和审批；
- 支持全额和部分退款；
- 退款必须关联原支付；
- 退款状态通过回调和主动查询确认；
- 已开票退款进入红冲或重开流程；
- 每日进行支付和退款对账。

## 十三、面料与供应商规范

- 门店只选择世尚面料编号；
- 供应商和供应商原始编号默认不向门店展示；
- 一个世尚面料编号可以关联多个历史供应商；
- 映射使用生效和失效时间；
- 更换默认供应商不得覆盖历史映射；
- 生产分配时保存实际供应商、原始编号和批次快照；
- 已分配供应商的历史生产单不随默认供应商变化；
- 新供应商产品不能保持一致时必须新建世尚面料编号；
- 供应商采购价和门店销售价独立管理。

## 十四、API契约

### 14.1 统一响应

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "req_01HXYZ"
}
```

统一格式不能替代正确HTTP状态码。

### 14.2 HTTP状态码

- `200`：成功；
- `201`：创建成功；
- `400`：参数错误；
- `401`：未认证；
- `403`：无权限；
- `404`：资源不存在；
- `409`：库存、状态或重复请求冲突；
- `422`：业务校验不通过；
- `429`：请求过于频繁；
- `500`：服务器错误。

### 14.3 业务错误码

- `0`：成功；
- `1xxx`：参数和格式；
- `2xxx`：认证和令牌；
- `3xxx`：权限和数据访问；
- `4xxx`：业务冲突、库存、状态、价格和支付；
- `5xxx`：系统、数据库和第三方服务。

示例：

- `4001`：套件库存不足；
- `4002`：订单价格已失效；
- `4003`：非法订单状态转换；
- `4004`：订单已进入生产；
- `4101`：支付回调已处理；
- `4102`：支付金额不一致；
- `4201`：面料已下架；
- `4202`：尺寸超出范围。

### 14.4 分页

请求：

```text
page=1&page_size=20
```

规则：

- `page`最小1；
- `page_size`默认20，最大100；
- 排序字段必须使用白名单。

响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [],
    "page": 1,
    "page_size": 20,
    "total": 0
  },
  "request_id": "req_01HXYZ"
}
```

### 14.5 幂等

以下接口必须支持幂等键：

- 创建订单；
- 锁定库存；
- 创建支付；
- 支付回调；
- 发起退款；
- 管理员取消；
- CRM同步。

## 十五、身份认证与权限

### 15.1 手机号账号

- 微信小程序和H5通过手机号关联同一账号；
- 小程序在手机号基础上绑定OpenID/UnionID；
- 验证码有效期建议5分钟；
- 验证码只能使用一次；
- 限制发送频率、单日次数和错误尝试；
- 登录令牌必须可撤销；
- 手机号变更需要安全验证。

### 15.2 RBAC与数据权限

- 功能权限和数据权限分开；
- 门店只能访问自己的订单、库存、地址和客户；
- 合伙人只能访问授权门店；
- 公司销售只能访问归属客户或授权数据；
- 管理员分级，禁止所有后台账号拥有超级权限；
- 敏感操作建议二次验证；
- 权限变更写审计日志；
- 员工离职立即停用账号并完成客户转交。

---

## 十六、安全与隐私

- 遵循最小必要信息原则；
- 手机号和地址按权限脱敏；
- 数据导出需要权限并写日志；
- 日志禁止记录验证码、令牌和密钥；
- 防范SQL注入、XSS、CSRF、越权和文件上传攻击；
- CORS使用白名单；
- 所有生产流量使用HTTPS；
- 上传文件限制类型、大小和数量；
- 上传文件重命名并进行安全校验；
- 依赖包定期进行安全扫描；
- 生产数据库和客户数据不得直接提交给AI工具；
- 支付回调以验签为核心，不把来源IP作为唯一凭证。

---

## 十七、异步任务与WebSocket

### 17.1 异步任务

以下工作应异步化：

- 短信和订阅消息；
- CRM同步；
- 生产通知；
- 支付补偿和主动查单；
- 发票通知；
- 统计更新。

要求：

- 任务具有唯一幂等键；
- 支持重试和退避；
- 永久失败进入人工处理；
- 多实例定时任务不能重复执行；
- 关键失败必须告警。

### 17.2 Workerman

Workerman仅用于：

- 后台新订单提醒；
- 订单状态实时通知；
- 生产和发货状态提示。

系统不能依赖WebSocket完成核心交易。断线后通过普通API刷新仍应获得正确状态。

## 十九、测试规范

- 客户和销售归属；

## 二十、Git与协作规范

### 20.1 分支与提交

- 主分支禁止直接推送；
- 使用功能分支和Pull Request；
- 至少一名人员Code Review；
- AI生成代码必须经过人工审查；
- 提交信息使用约定式提交。

示例：

```text
feat: 新增套件库存抵扣
fix: 修复支付回调重复核销
refactor: 重构订单状态转换服务
docs: 更新订货系统接口规范
test: 增加库存并发测试
```

### 20.2 协作协议

1. 收到任务先确认目标、方案、影响范围和验收条件，确认后编码；
2. 产出必须说明文件路径、变更内容、影响范围和测试结果；
3. 需要老板决定的事项使用“⚠️ 待决策”；
4. 引用其他Agent产出时注明来源文件和版本；
5. 只处理授权范围内任务，跨范围影响提交项目负责人；
6. 未经确认不得修改冻结的价格、库存、支付和归属规则；
7. 数据库和API变化必须同步更新文档；
8. 破坏兼容性的API变化必须升级版本；
9. CRM、支付和生产系统的外部写入必须明确审批和环境；
10. 不得用虚假数据冒充测试通过。

### 20.3 PR说明

每个PR至少包含：

- 需求来源；
- 实现方案；
- 修改文件；
- 数据库变更；
- API变更；
- 影响范围；
- 测试用例和结果；
- 风险和回滚方式；
- 截图或接口示例。
