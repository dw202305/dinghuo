# API 契约变更补丁文档（2026-08-18 全量修复）

> 适用范围：后端分支 `fix/full-audit-repair`（0ba3191 / 1eb8ed2 / b93ab39）起的接口契约。
> 本文档为 `docs/api.md` 的**增量补丁**，冲突处以本文档为准；`api.md` 原文保持不变。
> 面向对象：管理端 / 商城端前端联调人员。

## 一、HTTP 状态码不再恒 200（最重要）

此前所有接口无论成败均返回 HTTP 200，本次修复后业务错误码会映射为真实 HTTP 状态码（实现于 `ErrorCode::toHttpStatus`）。

### 1.1 分段映射表

| 错误码段 | 语义 | HTTP 状态码 |
|----------|------|------------|
| 0 | 成功 | 200 |
| 1xxx | 参数类（PARAM_INVALID / PARAM_MISSING / FORMAT_ERROR） | 400 |
| 2xxx | 认证类（UNAUTHENTICATED / TOKEN_EXPIRED / TOKEN_INVALID / WECHAT_NOT_BOUND） | 401 |
| 3xxx | 权限类（FORBIDDEN→403，DATA_NOT_FOUND→404） | 403 / 404 |
| 4xxx | 业务冲突/校验类 | 409 或 422（见 1.2） |
| 4029 | 限流 RATE_LIMITED | 429 |
| 5xxx | 系统类（SYSTEM_ERROR / DATABASE_ERROR→500，THIRD_PARTY_ERROR→502） | 500 / 502 |
| 未登记码 | 按段推断：1xxx→400，2xxx→401，3xxx→403，4xxx→422，其余→500 | 同左 |

### 1.2 4xxx 明细（逐个）

| 错误码 | 常量 | HTTP | 说明 |
|--------|------|------|------|
| 4001 | INVENTORY_INSUFFICIENT | 409 | 套件库存不足 |
| 4002 | PRICE_EXPIRED | 422 | 订单价格已失效（价格锁定 30 天） |
| 4003 | ILLEGAL_STATUS_TRANSITION | 409 | 非法订单状态转换 |
| 4004 | ORDER_IN_PRODUCTION | 409 | 订单已投产，不可取消/修改 |
| 4029 | RATE_LIMITED | 429 | 触发限流（新增，如验证码 60 秒防刷） |
| 4101 / 4105 | PAYMENT_CALLBACK_PROCESSED / BALANCE_CALLBACK_PROCESSED | 409 | 支付/储值回调已处理（幂等拦截） |
| 4102 | PAYMENT_AMOUNT_MISMATCH | 422 | 支付金额与订单金额不一致（阻断入账） |
| 4103 | BALANCE_INSUFFICIENT | 422 | 余额不足 |
| 4104 | MIXED_PAYMENT_NOT_SUPPORTED | 422 | 不支持混合支付 |
| 4106 | ACCOUNT_FROZEN | 422 | 资金账户已冻结 |
| 4201 | FABRIC_OFF_SHELF | 422 | 面料已下架 |
| 4202 | SIZE_OUT_OF_RANGE | 422 | 尺寸超出标准范围 |

### 1.3 前端对接要求

- 响应体结构不变：`{ code, message, data }`，**成功与否以 `code === 0` 判断**；
- axios / uni.request 拦截器不得再以 `status === 200` 作为成功条件，4xx/5xx 时仍需解析响应体取 `code` 与 `message`；
- 401（含 token 过期）统一走重新登录；429 提示稍后重试；
- CORS 已收紧为白名单（后端 `[CORS] ALLOWED_ORIGINS`），新增前端域名须在后端配置放行。

## 二、破坏性变更清单

### 2.1 payment_channel：int → string

- **变更**：所有响应中的支付渠道字段由整型改为字符串。
- **取值**：`balance`（余额）/ `wechat`（微信）/ `alipay`（支付宝）；资金流水中另可能出现 `offline` / `test`。
- **影响接口**：支付单详情/列表、订单详情中的支付信息、余额流水等一切返回 `payment_channel` 的接口。
- **前端动作**：去掉数字到渠道的映射表，改为字符串匹配；入参提交渠道同样传字符串。

### 2.2 订单接口支持 order_id / order_no 双参数

- **变更**：订单相关接口（详情、取消、支付、预审等）同时接受 `order_id`（数字主键）或 `order_no`（订单号）参数，服务端带回退解析（order_id 优先，缺失时回退 order_no）。
- **前端动作**：二者传其一即可，勿同时传冲突值；推荐已有 order_no 的页面直接传 order_no。

### 2.3 submit 需 confirmed=1；预审走新端点

- **变更**：
  1. `POST v1/orders/:order_no/submit` 正式提交**必须携带 `confirmed=1`**（价格确认标记），否则不受理；
  2. 先审后付（pre_audit）场景：走不带 `confirmed` 的 submit，或调用新端点 `POST v1/orders/:order_no/pre-audit/request` 发起预审；
  3. 订单级防重：同一草稿重复 submit 由服务端幂等拦截（返回已提交订单，不报错）。
- **前端动作**：商城端提交确认页补 `confirmed=1`；预审入口接新端点。

### 2.4 fabricStock 返回数组

- **变更**：`GET v1/inventory/fabric-stock` 返回结构改为**数组**（面料库存条目列表，字段含 fabric_no 及库存状态信息）。
- **备注**：当前为骨架返回，真实库存数据源待接入；前端按数组渲染并做好空数组兼容。

### 2.5 recharge 入参 meta.payer_name 不再落库

- **变更**：`POST v1/balance-accounts/:id/recharge` 入参中 `meta.payer_name` 仍被接受（兼容旧端），但**不再持久化**；付款人信息以审核凭证/线下备注为准。
- **前端动作**：无需展示该字段的回读值；可不传。

### 2.6 refundToBalance 响应删除 refund_no

- **变更**：退款到余额接口的响应中**删除 `refund_no` 字段**；退款结果以余额流水（`balance_transaction`）与订单状态为准。
- **前端动作**：移除对响应 `refund_no` 的读取与展示，改用流水号或提示信息。

## 四、其他联调须知（非破坏性）

1. **支付回调**：后端已接验签骨架（`PAY_VERIFY_STRICT` 开关），金额不一致不入账；联调环境可用 Mock 渠道。
2. **短信验证码**：`sendCode` 当前为 Mock 下发（AliyunSmsSender 待实现），联调时验证码从日志获取。
3. **微信登录**：`wechatLogin` 为适配层骨架 + Mock，真实凭证联调前排期处理。
4. **非标尺寸**：标准范围（宽 90-350cm / 高 50-600cm）外仅标记提示不拦截；硬限（宽 30-500cm / 高 20-800cm）外直接拒绝（错误码走参数/业务校验段，HTTP 400/422）。硬限取值待总部工艺确认，可能调整。
5. **幂等**：支付/储值/库存操作均为业务幂等键保护，重复提交返回首次结果而非报错。
